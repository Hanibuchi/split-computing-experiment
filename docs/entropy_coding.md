## 1. ひとことで言うと

> **0 次の適応算術符号化**（adaptive arithmetic coding）。頻度モデルは**ラプラス推定**（出現数を 1 から数え始める）で、
> **パケットごとにモデルを初期化**している。

- **算術符号化**: 記号列全体を 0〜1 の間の 1 つの数で表す、エントロピー符号化の標準的な方法（ハフマン符号と並んで教科書に必ず載っている）
- **適応**: 頻度表を送らず、符号化しながら出現数を数えて更新する。送り手と受け手が同じ手順で数えるので、表を送らなくても一致する
- **パケットごとに初期化**: パケット単体で復号できるので、ロスしたパケットの要素だけが欠ける。
  H.264 で、スライスの先頭ごとに CABAC の状態を初期化して、スライス単体で復号できるようにしているのと同じ考え方
- 古典的な文献: I. H. Witten, R. M. Neal, J. G. Cleary, "Arithmetic Coding for Data Compression," *Communications of the ACM*, 1987
  （カウントを 1 から始める適応モデルは、この論文の例そのもの）

## 2. 用語: 「0 次」と「ラプラス推定」

### 「0 次」= 直前の記号をいくつ見て確率を決めるか

次数はデータの次元ではなく、**文脈の長さ**です。

| 次数 | 確率の決め方 | 例 |
|---|---|---|
| **0 次** | 前後を見ず、記号ごとの出現頻度だけを使う | 今の実装。「0 が 70%、1 が 10%…」 |
| 1 次 | 直前の 1 記号ごとに、別々の頻度表を使う | 「直前が 0 なら次も 0 の確率は 90%」 |
| n 次 | 直前の n 記号を文脈にする | テキスト圧縮の PPM など |

- 論文（Shiba et al.）の式 (29) のエントロピーも 0 次エントロピーなので、今の実装は論文と同じ前提
- 文脈は直前の記号に限らない。特徴量なら「隣の要素の値」「どのチャネルか」「前フレームの同じ位置の値」などが使える。
  文脈ごとに頻度表を分けるのが CABAC の「Context Adaptive」。ただし表が増えるほど、学習コスト（[3 章](#3-確率の決め方を例でたどる)）も増える

### ラプラス推定 = まだ見ていない記号にも少し確率を残す

- 単純に `出現数 / 総数` で確率を決めると、まだ出ていない記号の確率が 0 になる。
  確率 0 の記号は算術符号で表せない（区間の幅が 0 になる）ので、その記号が出た瞬間に破綻する
- そこで全記号の出現数に α=1 を足して `(c_s + α) / (n + αK)` とする（K は記号の種類数）。加算スムージングとも呼ぶ
- 名前の由来はラプラスの「継続則」（n 日続けて太陽が昇ったら、明日も昇る確率は (n+1)/(n+2)）
- ベイズ的には、確率分布に一様な事前分布（ディリクレ分布 Dir(α, …, α)）を置いたときの事後平均。
  α=1/2 にしたものは **KT 推定量**（Krichevsky–Trofimov）と呼ばれる
- **α の意味**: 最初に足しておく出現数。小さいと、使わない記号に配る確率が減ってよく出る記号を早く学べるが、
  珍しい記号が初めて出たときは高くつく。大きいと確率が均等に近いまま動きにくい

> 注意: 「ラプラス推定」はラプラス分布とは関係ありません（[9 章](#9-改善の余地未実装)に出てくる「離散化した Laplace 分布」とは別物）。

## 3. 確率の決め方を例でたどる

2bit 量子化（記号は −2, −1, 0, 1 の K=4 種類）で、1 パケットの中身が `0, 0, 1, 0, −1, 0` だったとします。
送り手は次の手順を繰り返します。

1. パケットの先頭で、全記号の出現数を 1 にする
2. 次の記号の確率を `その記号の出現数 / 出現数の合計` とする
3. その確率で算術符号化する（確率 p の記号は約 −log2 p ビット）
4. 符号化した記号の出現数を +1 する

| 手順 | 符号化する値 | そのときの出現数 [−2, −1, 0, 1] | 確率 | 符号長 |
|---|---|---|---|---|
| 1 | 0 | [1, 1, 1, 1]（合計 4） | 1/4 | 2.00 bit |
| 2 | 0 | [1, 1, **2**, 1]（合計 5） | 2/5 | 1.32 bit |
| 3 | 1 | [1, 1, 3, 1]（合計 6） | 1/6 | 2.58 bit |
| 4 | 0 | [1, 1, 3, **2**]（合計 7） | 3/7 | 1.22 bit |
| 5 | −1 | [1, 1, 4, 2]（合計 8） | 1/8 | 3.00 bit |
| 6 | 0 | [1, **2**, 4, 2]（合計 9） | 4/9 | 1.17 bit |
| | | | **合計** | **11.3 bit** |

0 の確率が 1/4 → 2/5 → 3/7 → 4/9 と上がっていき、「0 が多い」ことを符号化しながら覚えていくのが分かります。

### 学習コスト

このパケットの実際の割合（0 が 4/6、1 と −1 がそれぞれ 1/6）を最初から知っていれば、
0 次エントロピーは 1.25 bit/要素で、6 要素で **7.5 bit** です。
差の約 3.8 bit が、**分布を知らない状態から学ぶためのコスト（学習コスト）**です。

### 符号長は記号の順番によらない

各手順の確率を掛け合わせると、

- 分子: 記号ごとに 1·2·3·… と増えていく → 0 の分は 1·2·3·4 = 24、1 と −1 の分はそれぞれ 1
- 分母: 4·5·6·7·8·9 = 60480（毎回 1 ずつ増える）

となり、どちらも**各記号の出現数だけ**で決まります。符号長は log2(60480 / 24) = 11.3 bit で、上の表の合計と一致します。
これをガンマ関数で一般化したのが `adaptive_code_bits` の式です。

```
符号長 [bit] = log2 Γ(n + αK)/Γ(αK) − Σ_s log2 Γ(c_s + α)/Γ(α)
```

このおかげで、実際に算術符号器を動かさなくても、パケット内の記号の出現数から正確な符号長が計算できます。

## 4. 算術符号の符号化と復号

### 符号化（送り手）: 区間を狭めていく

区間 [0, 1) から始めます。毎回、今の区間を出現数に比例して 4 つに分け（並びは −2, −1, 0, 1）、
符号化する記号の部分を新しい区間にします。

| 手順 | 記号 | 出現数 [−2, −1, 0, 1] | 選ぶ部分 | 新しい区間 | 区間の幅 |
|---|---|---|---|---|---|
| 1 | 0 | [1, 1, 1, 1] | 3 番目（2/4〜3/4） | [0.5, 0.75) | 1/4 |
| 2 | 0 | [1, 1, 2, 1] | 3 番目（2/5〜4/5） | [0.6, 0.7) | 1/10 |
| 3 | 1 | [1, 1, 3, 1] | 4 番目（5/6〜6/6） | [0.68333, 0.7) | 1/60 |
| 4 | 0 | [1, 1, 3, 2] | 3 番目（2/7〜5/7） | [0.68810, 0.69524) | 1/140 |
| 5 | −1 | [1, 1, 4, 2] | 2 番目（1/8〜2/8） | [0.68899, 0.68988) | 1/1120 |
| 6 | 0 | [1, 2, 4, 2] | 3 番目（3/9〜7/9） | [0.689286, 0.689683) | 1/2520 |

- 区間の幅は各手順の確率の積。最後の幅 1/2520 は、[3 章](#3-確率の決め方を例でたどる)の 11.3 bit（log2 2520 ≈ 11.3）に対応する
- 最後の区間に入る数のうち、2 進数で短く書けるものを送る。今回は 0.689453125 = 0.101100001₂ が入るので `101100001` の 9 bit
  - 9 bit で済んだのはたまたま。一般には約 −log2(区間の幅) bit、確実に区間内に収めるにはさらに 1〜2 bit 必要。
    この端数を見込んだのが `AC_TAIL_BYTES`（2 バイト）

### 復号（受け手）: v がどの区間に入るかをたどる

受け手が持っているのは、受け取った数 **v = 0.689453125** と、ヘッダの**要素数 6** だけです。
送り手と同じく出現数をすべて 1 から始め、同じ規則で区間を分けて、v が入る部分の記号を出力し、その記号の出現数を +1 します。

| 手順 | 今の区間を出現数で 4 つに分けた境界 | v が入る部分 | 出力 | 更新後の出現数 |
|---|---|---|---|---|
| 1 | [0, 0.25, 0.5, 0.75, 1) | 0.5〜0.75 | **0** | [1, 1, 2, 1] |
| 2 | [0.5, 0.55, 0.6, 0.7, 0.75) | 0.6〜0.7 | **0** | [1, 1, 3, 1] |
| 3 | [0.6, 0.6167, 0.6333, 0.6833, 0.7) | 0.6833〜0.7 | **1** | [1, 1, 3, 2] |
| 4 | [0.68333, 0.68571, 0.68810, 0.69524, 0.7) | 0.68810〜0.69524 | **0** | [1, 1, 4, 2] |
| 5 | [0.68810, 0.68899, 0.68988, 0.69345, 0.69524) | 0.68899〜0.68988 | **−1** | [1, 2, 4, 2] |
| 6 | [0.68899, 0.68909, 0.68929, 0.68968, 0.68988) | 0.68929〜0.68968 | **0** | （終了） |

6 個取り出したらヘッダの要素数に達したので止めます。元の `0, 0, 1, 0, −1, 0` が戻りました。

### ポイント

- **受け手が同じ区間を作れる理由**: 区間の分け方は出現数だけで決まり、その出現数は「すでに復号した記号」から受け手も数えられる。
  だから頻度表を送らなくてよい
- **要素数がヘッダに必要な理由**: v はどこまで狭めても必ずどれかの区間に入るので、止めどきが分からない。
  そのため要素数を送る（`AC_HEADER_BYTES` に含まれる u32）
- **実際の符号器では**: 小数のままだと精度が足りないので整数演算で区間を表し、上位ビットが確定するたびに出力して
  区間を広げ直す（正規化）。これで長い列も有限の精度で扱える

## 5. パケットをまたいで符号化しない理由

v の値は、**先頭のビットから全部そろって初めて**決まります。

- フレーム全体（複数パケット）を 1 本の算術符号にすると、途中のパケットが 1 つ落ちただけで v が分からなくなり、
  それ以降の要素がすべて復号できなくなる
- パケットごとに区間 [0, 1) と出現数をリセットしておけば、各パケットが単体で復号できるので、
  **落ちたパケットに入っていた要素だけ**が欠ける

その代わり、パケットごとに頻度表をゼロから学び直す（[3 章](#3-確率の決め方を例でたどる)の学習コストがパケットごとにかかる）のが代償です。

前フレームの頻度表を使い回す方法も考えられますが、前フレームのパケットが落ちると送り手と受け手で表がずれて
復号できなくなるので、ロスのある通信路には向きません。

## 6. パケットへの詰め方

「先にパケットに分割してから符号化する」と思いがちですが、実装はそうなっていません。

- **interleave=False（既定）**: 要素ごとの符号長を累積しながら、ペイロード（MTU − ヘッダ − 終端）に**収まる限界まで**詰める
  （`_incremental_bits` で累積の符号長を出し、`searchsorted` で収まる要素数を求める）。
  空きは 1 パケットあたり数バイトで、**MTU の使用率は約 99%**
- **interleave=True**: 要素 i をパケット i mod P に入れる。全パケットが MTU に収まるまで P を増やすので、
  一部のパケットに空きが出て、使用率は約 97.5%

1 パケットのバイト数は次のとおりです。

```
ヘッダ 21 B（AC_HEADER_BYTES） + ceil(符号長 / 8) + 終端 2 B（AC_TAIL_BYTES）
ヘッダの中身: フレーム番号 u32 + 種類 u8 + 連番 u16 + パケット数 u16 + オフセット u32 + q f32 + 要素数 u32
```

比較用の固定長方式（`frame_bytes`）では、各要素を b ビットで詰め、ヘッダは要素数を除いた 17 B（`HEADER_BYTES`）です。

- **理想値** = フレーム全体の 0 次エントロピー（出力 CSV の `entropy_bpe`）× 要素数 / 8。ヘッダを含まない
- **理想値との差**には、ヘッダ・終端（約 1.6%）と学習コストの両方が入っている
- **固定長比** = b ビット固定長の何分の 1 になったか。算術符号を使うことで得られる効果

### 読み取れること

1. **2bit・4bit では理想値との差がおおむね 2〜4%**で、ほぼ理想どおり。
   D+DZ の P フレームはほとんどが 0 なので、エントロピーが 0.2〜1.2 bit/要素まで下がり、固定長の 3〜11 倍縮む
2. **8bit では理想値との差が 9〜11%**。K=256 で使わない記号に確率を配り続ける学習コスト（[9 章](#9-改善の余地未実装)）。改善の余地があるのはここ
3. **MobileNet の 2bit が +11%** なのは学習コストではなく、1 フレームが 0.27 KB しかなく、ヘッダと終端の約 23 B が相対的に大きいため
4. 一部の条件（ResNet50 F+Sym 4bit で −1.0%）では算術符号が理想値を**下回る**。
   パケットごとに頻度表を初期化するので、チャネルごとに違う分布にも適応でき、
   フレーム全体で 1 つの分布を仮定した 0 次エントロピーより短くなることがある

## 8. ハフマン符号との比較

**一般には算術符号の方が圧縮率は高く、ハフマン符号は速くて実装が簡単**、という関係です。

- 「ハフマン符号は最適」というのは、**1 記号ごとに整数ビットの符号語を割り当てる方式（記号単位の接頭符号）の中で**最適、という意味
- 算術符号は記号列全体を 1 つの数で表すので、この制約を受けず、1 記号あたり 0.2 bit のような半端な長さも実現できる

### この実験でハフマン符号が向かない理由

**1. 1 要素あたり最低 1 bit かかる（最大の理由）**

| 条件 | 0 次エントロピー | 算術符号 | ハフマン符号（下限） |
|---|---|---|---|
| ResNet50 L2・2bit（D+DZ） | 0.18 bit/要素 | 9.0 KB | **50 KB 以上**（1 bit × 40 万要素） |
| VGG16 16・4bit（D+DZ） | 0.70 bit/要素 | 18.1 KB | **25 KB 以上** |

2bit だとハフマン符号でも固定長（2 bit/要素）の半分にしかならないが、算術符号なら 1/11 になる。

**2. 符号表を送るか、適応させる必要がある**
- ハフマン符号は符号表を先に決める必要があり、パケットごとに送るとオーバーヘッドになる
- 適応型ハフマン符号もあるが、木の更新が複雑で、圧縮率も適応算術符号に及ばない
- 算術符号は、確率を決めるモデルと符号化の処理が完全に分かれているので、モデルを差し替えるだけで
  適応・文脈モデル・事前分布などを組み込める

**3. ハフマン符号で 1 bit の壁を越えようとすると複雑になる**
- 0 の連続を長さで表してから符号化する（ランレングス＋ハフマン。JPEG の方式）、
  複数の記号をまとめて 1 記号として扱う（拡張ハフマン）などの工夫が要り、それでも算術符号には届きにくい

### ハフマン符号が「良い」と言われてきた背景

- **速い**: 表を引くだけで符号化・復号でき、ハードウェアにも載せやすい
- **特許の歴史**: かつて算術符号には IBM などの特許があり、JPEG の算術符号モードはほぼ使われなかった
- **近年**: 特許は切れ、rANS（Zstandard や学習ベースの画像圧縮で使われる）のように、
  算術符号並みの圧縮率でハフマン符号並みに速い方式もある

この実験は計算速度ではなく送信量を評価しているので、理想値に最も近い算術符号を前提にしています。

## 9. 改善の余地（未実装）

8bit での学習コストが大きい原因は、**K=256 の全記号に出現数 1 の下駄を履かせて始める**ことです。

- 一番よく出る 0 でも、最初は確率 1/256 で 8 bit かかる
- 実際に出る値が数十種類でも、残りの約 200 記号が確率を取り続ける。
  例: 1000 要素符号化した時点で、合計 1256 のうち 200（約 16%）が一度も出ない記号の分。
  出る記号すべてが毎回 −log2(0.84) ≈ 0.25 bit ずつ余分にかかる
- 4bit（K=16）なら下駄は小さいので、学習コストも小さい

### 対策案と効果の目安

合成データ（Laplace 分布の整数、256ch×28×28 要素、MTU 1400）で、学習コスト（理想値からの増加分）を比べた結果です。

| 方式 | 4bit | 8bit・広い分布 | 8bit・狭い分布 | パケット単体で復号できるか |
|---|---|---|---|---|
| 現行（α=1） | 422 B | 10,992 B | 9,519 B | ○ |
| α=0.1 にする | 396 B | 4,372 B | 2,188 B | ○（定数を変えるだけ） |
| パラメトリックな分布（スケール 1 個をヘッダで送る） | 40 B | 13 B | 9 B | ○ |
| パラメトリックな分布を初期値にして適応 | 375 B | 3,138 B | 715 B | ○ |

1. **α を小さくする**: `AC_ALPHA` を変えるだけ。適した値は分布によるので、実データで決める必要がある
2. **パラメトリックなモデル**: フレームごとに分布の形（離散化した Laplace やガウスなど）のスケールを推定し、
   全パケットのヘッダに入れる（+2〜4 B）。学習コストはほぼ 0。
   ただし上の数字はデータが本当に Laplace だから出たもので、実際の特徴量
   （ReLU 後の I フレームは 0 に大きなピークがある片側の分布）では分布の形が合わない分のロスが出る
3. **パラメトリックな初期値＋適応**: 2 のヘッダ情報で頻度表を初期化してから適応させる。形が合わなくても適応で補える
4. **二値化して文脈を分ける**（CABAC のように「0 かどうか・符号・大きさ」に分ける）: 実質的な記号数が減り、学習が速くなる。実装は重め
5. **オフラインで学習した固定の頻度表**: 分割点とビット数ごとに学習データから表を作っておく。ヘッダは増えないが、分布がずれると効率が落ちる

まずは実際の UCF101 の特徴量（I フレームと P フレームの差分の両方）で、どれが効くかを測るのがよい。
